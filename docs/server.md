# Подключение будущего сервера

Один экземпляр API обслуживает и REST, и статический веб. PostgreSQL хранит пользователей, заказы, историю рейсов и журналы учёта. Компоненты общаются по обычным HTTP и PostgreSQL. Переезд меняет конфигурацию и сетевые адреса.

## Параметры

| Назначение | Настройка |
| --- | --- |
| HTTP | `API_HOST`, `API_PORT`. В Compose `API_HOST` определяет внешний интерфейс публикации, внутри контейнера API слушает все интерфейсы |
| БД | Учётные данные `POSTGRES_*` в Compose или внешний `DATABASE_URL`. Для отдельного подключения доступны стандартные переменные драйвера pg |
| Сессии | `SESSION_HOURS`. В базе хранится хеш токена. При смене пароля отзываются все сессии пользователя |
| База производства | `BASE_ADDRESS`, необязательные `BASE_LAT` и `BASE_LON`, `BUSINESS_TZ` |
| Демо | `SEED_DEMO`, `DEMO_PASSWORD`, `DEMO_WATER_PRICE_KOP`. Для отдельной рабочей БД задать `SEED_DEMO=false` при первом запуске |
| Маршруты | `MAP_PROVIDER=demo`, `DEMO_LEG_MINUTES`, `STOP_BASE_MINUTES`, `STOP_PER_BOTTLE_MINUTES`, `RELOAD_MINUTES`, `FLOOR_MINUTES`, `CHECKPOINT_MINUTES`, `LOADER_FACTOR` |
| Картографическая подложка | `MAP_TILES_ENABLED=true` по умолчанию разрешает клиенту показывать стандартные уличные тайлы OSM. Для автономного обзора Natural Earth установите `false` |
| Поиск адресов | `GEOCODER_ENABLED=true`, `GEOCODER_URL=https://photon.komoot.io/api/`. Для своего Photon задайте HTTP(S)-адрес его endpoint `/api/`, доступный процессу API. Интервал между запросами к геокодеру задаёт `GEOCODER_MIN_INTERVAL_MS` (1000), таймаут — `GEOCODER_TIMEOUT_MS` (5000) |
| Android | `ANDROID_API_URL` на этапе сборки, на сервере — HTTPS origin |

## Первичная настройка

Для первого приёмочного стенда достаточно Linux VPS с 2 vCPU, 4 ГБ RAM и SSD от 40 ГБ, если PostgreSQL и веб работают на одной машине, а дорожный сервис подключён отдельно. Укажите A-запись домена на IP сервера и откройте TCP 80/443. SSH используйте с ключом. Доступ к PostgreSQL и внутреннему порту API проходит через контейнерную сеть. Caddy получает и продлевает TLS-сертификат.

Из корня клона на VPS:

```bash
umask 077
cp .env.vps.example .env.vps
# Вставьте свой домен и уникальное значение POSTGRES_PASSWORD.
openssl rand -hex 24
docker compose --env-file .env.vps -f deploy/compose.vps.yml config --quiet
docker compose --env-file .env.vps -f deploy/compose.vps.yml up --build -d --wait
curl -fsS https://ВАШ-ДОМЕН/health/ready
bash deploy/backup.sh
```

Откройте домен в браузере и пройдите «Создать аккаунт → Я организую доставку». В «Команда → Адрес и координаты базы» введите производство. В каталоге добавьте бренды, затем машины и смены. Приглашения сотрудников используют код с назначенной ролью и сроком 48 часов. Для приёмки с тестовыми точками можно включить `GEOCODER_ENABLED` и `ROAD_ROUTER_ENABLED`. Для постоянного использования задайте согласованные адресные и дорожные сервисы. Публичный OSRM показывает среднее дорожное время. Отдельный OSRM с данными региона готовится как самостоятельный сервис.

Для сборки Android к этому стенду задайте `ANDROID_API_URL=https://ВАШ-ДОМЕН` и запустите `apps/android/build-local.ps1` без флага `-Usb`. После подготовки постоянного ключа подписи используйте его для обновлений Android.

Для обновления сохраните `bash deploy/backup.sh`, обновите checkout до выбранного коммита и повторите `docker compose … up --build -d --wait`. Скрипт создаёт архив с закрытыми правами и проверяет его читаемость. Для восстановления откройте отдельную пустую БД. Храните копию вне VPS. CI проверяет запуск стека за Caddy и восстановление дампа в отдельную одноразовую БД.

### Выкладка тестового стенда через GitHub Actions

`Release staging` запускается вручную только из `main`. В окружении GitHub `staging` задайте переменные `STAGING_SITE_URL` с HTTPS-адресом панели, `STAGING_HOST` с SSH-адресом и `STAGING_SSH_KNOWN_HOSTS` с проверенным ключом хоста. Секреты `STAGING_SSH_PRIVATE_KEY`, `STAGING_ANDROID_KEYSTORE` (PKCS#12 в Base64) и `STAGING_ANDROID_KEYSTORE_PASSWORD` хранятся в GitHub. Псевдоним ключа подписи APK — `farvater-staging`.

На VPS checkout `main` и `.env.vps` находятся в `/opt/farvater`, владелец — `farvater-deploy`. Этому пользователю нужен доступ к Docker. Скопируйте `deploy/staging-release.sh` в `/usr/local/sbin/farvater-staging-release` с владельцем `root` и режимом `0755`. Для ключа выкладки укажите `restrict,command="/usr/local/sbin/farvater-staging-release"` в `authorized_keys`. Приватный ключ администратора и приватный ключ выкладки должны различаться.

Выкладка проверяет подпись APK, создаёт копию существующей БД и обновляет стенд до проверенного коммита `main`. После успешного запуска новый APK появляется на экране входа и по пути `/downloads/farvater-driver.apk`. GitHub Actions проверяет HTTPS, готовность API и совпадение опубликованного файла с собранным APK. Флаг `build_only` оставляет подписанный APK в артефактах проверки и пропускает все шаги на VPS. Для обновления установленного приложения сохраняйте тот же ключ подписи. При переходе со старого debug APK с другой подписью понадобится удалить debug-версию перед установкой.

### Выгрузка в Google Таблицы

Назначьте отдельный лист, доступный сервисному аккаунту Google на редактирование, и включите Sheets API в его проекте. В `.env.vps` заполните `SHEETS_TEAM_ID`, `SHEETS_SPREADSHEET_ID`, `SHEETS_TAB`, `SHEETS_CLIENT_EMAIL` и `SHEETS_PRIVATE_KEY` (в многострочном значении или с `\n`) и установите `SHEETS_EXPORT_ENABLED=true`. Интеграция ставит в очередь новые сдачи выбранной команды. Повторная отправка обновляет строку этого же отчёта. Колонки включают воду, тару, нал, безнал, вознаграждение и часы грузчика. Статус виден в «Отчётах».

### Настройка существующей базы

1. Выбрать домен и разместить API за HTTPS reverse proxy. Опубликовать через proxy единственный HTTP-порт приложения. PostgreSQL оставить в закрытой сети. Использовать отдельный каталог и том для каждого окружения.
2. Заполнить окружение на машине развёртывания, задать отдельные стойкие пароли, отключить демосид. Создать пустую PostgreSQL и предоставить доступ приложению. Смена `SEED_DEMO` влияет на начальное заполнение и сохраняет уже созданные учётные записи.
3. Запустить контейнер. Контроль готовности — успешный ответ `GET /health/ready`. В CI сборка и проверки отделены от размещения на сервере.
4. Создать первого администратора командой `node apps/api/src/account.js` в окружении API. Команда читает `ACCOUNT_NAME`, `ACCOUNT_EMAIL`, `ACCOUNT_ROLE=manager`, `ACCOUNT_PASSWORD`. Для существующей команды задайте `ACCOUNT_TEAM_ID` (по умолчанию `1`). Для новой команды задайте `ACCOUNT_TEAM_NAME`. При работе с PGlite перед командой остановите API и задайте тот же каталог БД. Деморежим создаёт пять кабинетов. Операторы и экспедиторы регистрируются по приглашению администратора.
5. В веб-панели руководитель создаёт персональные аккаунты сотрудников, а диспетчер заводит автомобили и назначает водителей на даты. Этим действиям соответствуют `POST /api/accounts`, `POST /api/vehicles` и `POST /api/shifts`. После подключения реальных устройств проверить вход каждой роли, публикацию и одну согласованную пробную смену.
6. Перед работой с клиентскими данными определить доступы сотрудников, сроки хранения, размещение персональных данных и процедуру восстановления доступа. Сборка для реального распространения потребует собственного ключа подписи Android.

## Резервные копии PostgreSQL

Команды ниже рассчитаны на POSIX-оболочку и утилиты PostgreSQL той же основной версии. Для пароля подходит защищённый `.pgpass`. Каталог для копий должен быть доступен только ответственному сотруднику.

```sh
umask 077
pg_dump --format=custom --file="$BACKUP_FILE" --dbname="$DATABASE_URL"
pg_restore --list "$BACKUP_FILE"
pg_restore --exit-on-error --no-owner --no-privileges --dbname="$EMPTY_VERIFY_DATABASE_URL" "$BACKUP_FILE"
```

`BACKUP_FILE` — новое имя файла с датой. `EMPTY_VERIFY_DATABASE_URL` — отдельная пустая база для проверки восстановления. После восстановления сравнить число заказов и значения сдачи последней закрытой смены с исходной БД. Перед миграцией сохранить проверенную копию и иметь согласованное окно обслуживания. Резервное копирование, расписание, хранение и тест восстановления на выбранном VPS предстоит настроить.

Учебную БД и демоучётные записи держать отдельно от рабочей. Файлы действующей базы находятся за пределами исходников. Google Диск синхронизирует файлы рабочей папки по своим правилам. `.gitignore` управляет составом Git.
