# Подключение будущего сервера

Один экземпляр API обслуживает и REST, и статический веб. PostgreSQL хранит пользователей, заказы, историю рейсов и журналы учёта. Компоненты общаются по обычным HTTP и PostgreSQL. Переезд меняет конфигурацию и сетевые адреса.

## Параметры

| Назначение | Настройка |
| --- | --- |
| HTTP | `API_HOST`, `API_PORT`. В Compose `API_HOST` определяет внешний интерфейс публикации, внутри контейнера API слушает все интерфейсы |
| БД | Учётные данные `POSTGRES_*` в Compose или внешний `DATABASE_URL`. Для отдельного подключения доступны стандартные переменные драйвера pg |
| Сессии | `SESSION_HOURS`. В базе хранится хеш токена. При смене пароля отзываются все сессии пользователя |
| База производства | `BASE_ADDRESS`, необязательные `BASE_LAT` и `BASE_LON`, `BUSINESS_TZ` |
| Демо | `SEED_DEMO`, `DEMO_PASSWORD`, `DEMO_WATER_PRICE_KOP`. Для отдельной рабочей БД задать `SEED_DEMO=false` при первом запуске |
| Маршруты | `MAP_PROVIDER=demo`, `DEMO_LEG_MINUTES`, `STOP_BASE_MINUTES`, `STOP_PER_BOTTLE_MINUTES`, `RELOAD_MINUTES`, `FLOOR_MINUTES`, `CHECKPOINT_MINUTES`, `LOADER_FACTOR` |
| Android | `ANDROID_API_URL` на этапе сборки, на сервере — HTTPS origin |

## Первичная настройка

1. Выбрать домен и разместить API за HTTPS reverse proxy. Опубликовать через proxy единственный HTTP-порт приложения. PostgreSQL оставить в закрытой сети. Использовать отдельный каталог и том для каждого окружения.
2. Заполнить окружение на машине развёртывания, задать отдельные стойкие пароли, отключить демосид. Создать пустую PostgreSQL и предоставить доступ приложению. Смена `SEED_DEMO` влияет на начальное заполнение и сохраняет уже созданные учётные записи.
3. Запустить контейнер. Контроль готовности — успешный ответ `GET /health/ready`. В CI сборка и проверки отделены от размещения на сервере.
4. Создать первого руководителя командой `node apps/api/src/account.js` в окружении API. Команда читает `ACCOUNT_NAME`, `ACCOUNT_EMAIL`, `ACCOUNT_ROLE=manager`, `ACCOUNT_PASSWORD` из окружения процесса. При работе с PGlite перед административной командой остановить API и задать тот же каталог БД. Деморежим сам создаёт пять кабинетов.
5. В веб-панели руководитель создаёт персональные аккаунты сотрудников, а диспетчер заводит автомобили и назначает водителей на даты. Этим действиям соответствуют `POST /api/accounts`, `POST /api/vehicles` и `POST /api/shifts`. После подключения реальных устройств проверить вход каждой роли, публикацию и одну согласованную пробную смену.
6. Перед работой с клиентскими данными определить доступы сотрудников, сроки хранения, размещение персональных данных и процедуру восстановления доступа. Сборка для реального распространения потребует собственного ключа подписи Android.

## Резервные копии PostgreSQL

Команды ниже рассчитаны на POSIX-оболочку и утилиты PostgreSQL той же основной версии. Для пароля подходит защищённый `.pgpass`. Каталог для копий должен быть доступен только ответственному сотруднику.

```sh
umask 077
pg_dump --format=custom --file="$BACKUP_FILE" --dbname="$DATABASE_URL"
pg_restore --list "$BACKUP_FILE"
pg_restore --exit-on-error --no-owner --no-privileges --dbname="$EMPTY_VERIFY_DATABASE_URL" "$BACKUP_FILE"
```

`BACKUP_FILE` — новое имя файла с датой. `EMPTY_VERIFY_DATABASE_URL` — отдельная пустая база для проверки восстановления. После восстановления сравнить число заказов и значения сдачи последней закрытой смены с исходной БД. Перед миграцией сохранить проверенную копию и иметь согласованное окно обслуживания. Резервное копирование, расписание, хранение и тест восстановления на выбранном VPS предстоит настроить.

Учебную БД и демоучётные записи держать отдельно от рабочей. Файлы действующей базы находятся за пределами исходников. Google Диск синхронизирует файлы рабочей папки по своим правилам. `.gitignore` управляет составом Git.
